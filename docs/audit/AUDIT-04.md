### 三条结论

1. **Xray 的"深度"是三家里最好的** —— 后量子加密、Argo、反向代理、
   证书指纹固定、浏览器拨测、端口冲突重分配，这些 M/SB 都没有。
   **不要在补外围的过程中把这些改坏。**

2. **Xray 的"面"是三家里最薄的** —— 协议档位、CDN、Share/Pull 全缺。
   而且缺的正好是"从服务端到客户端"这条链路。

3. **最大的单点缺口是 Client 与服务端零耦合。**
   目前唯一通路是：服务端打印链接 → 用户手动复制 → 粘贴到 Client。

## 2. 审计中发现的三个陷阱

写在这里是因为**每一处都可能导致误删或误判**。

### 陷阱一：`unused/xray_install.sh` 不是废弃脚本

目录名叫 `unused/`，但它是**面板菜单 1「安装/更新 xray」的活跃依赖**：

```bash
xray-panel.sh:111
XRAY_INSTALL_URL=".../main/unused/xray_install.sh"
```

2026-09 还在维护。**目录名是历史误会。** 清理时绝不能连目录一起删。
建议迁到 `bin/`（同步改 `xray-panel.sh:111` 和 `VEVLRE.sh:79`）。

### 陷阱二：孤儿链不能只删叶子

`Conversion.sh` / `VEVLRE.sh` / `ngcadall.sh` 这三个入口自己零引用，
但它们是 `caddy.sh` / `nginx.sh` / `conf/cconf.sh` / `conf/nconf.sh`
**唯一的调用来源**。

只删叶子 → 打断这三个入口 → 独立部署套件全线报废。
**必须整体决策，不能局部删。**

### 陷阱三：成对脚本不是 IPv4/IPv6 双版本

直觉会以为 `nginx6.sh` 是 IPv6 版。**不是。** 全项目 `IP_CHOICE` 的 24 处命中
都在旧代码里，运行时按 1/2 选 `0.0.0.0` vs `[::]`，**没有任何自动分派逻辑**。

| 一对 | 真实关系 | 证据 |
|---|---|---|
| `nginx.sh` ↔ `nginx6.sh` | 新旧两代 | `b4f45ea`(2026-04-20) 把旧版**重命名**保存为 nginx6.sh，同日重建新 nginx.sh；nginx6.sh 此后零提交 |
| `VEVLRE.sh` ↔ `VEVLRE6.sh` | 新旧两代 | 6 版把 IP 选择内联；新版下沉到 `conf/XRevise.sh:114-136`，diff 694 行 |
| `reality_xray.sh` ↔ `reality_xray_ip.sh` | **不同体系** | 两者装的是**官方 Xray**（`XTLS/Xray-install`，服务名 `xray`），**不属于 catmi 的 xrayls 体系**，停更 22 个月 |

## 4. 下一阶段实施计划

分五步，**每步结束都必须实机验证**，不要连着做。

### 第 1 步：零风险清理（不改功能）

| 动作 | 说明 |
|---|---|
| 删 13 个明确废弃文件 | 见清单，**不含 `conf/fd/` 那两个** |
| `unused/xray_install.sh` → `bin/xray_install.sh` | 同步改 `xray-panel.sh:111`、`VEVLRE.sh:79` |
| `conf/fd/` 老两版 → `conf/fd/legacy/` | 加 README 说明被 tunnel 版取代 |
| **验证** | 面板 9 项菜单逐项点一遍；菜单 1 安装、菜单 9 反代必须仍可用 |

⚠ 删之前必须先确认：`upxray.sh`(5行) 和 `uninstall_xray.sh`(5行) 真的是空壳，
别删错了。

### 第 2 步：补协议面（性价比最高）

| 动作 | 优先级 | 说明 |
|---|:---:|---|
| `conf/vlesswsecn.sh` → 接进菜单 | 🔴 | 脚本完整（19 函数），只是没接线。WS 是兼容性最好的传输 |
| **CDN 档位** | 🔴 | 最大缺口。M 的 `all.sh` CDN 组可直接参考 |
| Trojan + WS | 🟡 | Trojan REALITY 已在，WS 作回退 |
| VLESS + gRPC + REALITY | 🟡 | 兼容性最好的传输之一 |
| **ENC/ML-DSA 做成可选项** | 🔴 | **默认档位不能带**——M 客户端连不上 |

> CDN 档位必须实测 gRPC 是否真的通。
> M 项目实测：VLESS-gRPC-CDN 直连通但走 CDN 不通，VMess-gRPC-CDN 反而通。
> **不要假设，先测。**

### 第 3 步：Share（本次重点）

按 AUDIT-03 的顺序：

```
1. share_server.py      ← 抄 SB 版（最精简，无 build_sub 依赖）
2. token 元数据 + 生命周期（max_uses / expires_at / used_count）
3. 限次与过期菜单
4. 分享管理面板（列表/停用/换 token/撤销/随节点删除联动吊销）
5. 全量聚合产物        ← 最重，先统一各协议 YAML schema
```

**验证**：生成链接 → 客户端拉取 → 第二次拉返回 410 → 确认计数正确。

⚠ **不要**走 nginx/caddy 静态目录暴露 `out/` 的捷径——
那会绕过 token 和限次，等于把订阅变成公开目录。

### 第 4 步：Pull（Server → Client 打通）

```
1. 客户端订阅注册表（subscriptions.json：prefix/url/name/count）
2. 订阅更新命令 + 失败降级（备份→重拉→失败回滚，不删原节点）
3. 订阅自定义命名 + 来源前缀分组
4. 订阅自动更新开关（默认手动）
5. Client Web UI 的订阅管理页
6. 顺手把 4 个死代码按钮接上（diagnose/ech/config_update/node_use）
```

**验证**：服务端改配置 → 客户端一键更新 → 客户端能连上；
故意把服务端 token 吊销 → 客户端更新应**明确报错**而不是静默清空。

### 第 5 步：实机验证与门禁

- RN 上跑完整双端链路（服务端生成 → 分享 → 客户端拉取 → 实连）
- 反向代理实机验证（**重点查 nginx 冲突**——生产机 nginx 上还有 SB-Panel 的 CDN 段落）
- 建立机械门禁（参考 M 项目的 13 项）

## 5. 三条必须遵守的约束

### ① 不要重做 Client UI

Client Web UI 是成熟资产。缺的是**服务端对接**，不是 UI。
上面计划里所有 Client 相关的改动都是**加订阅管理页**，
不是重做现有界面。

### ② 不要重构 Outbound

`conf/outbound.sh` 2099 行，是全项目最成熟的模块。
本次审计**未发现明确问题**，按既定原则不动。

### ③ ENC 必须可关

`Reality.sh:388` 自己写了 M 内核兼容性的警告。
默认档位带 ML-KEM/ML-DSA 会让 M 客户端连不上。
**ENC 做成开关，默认关闭**，或至少在生成时明确提示。

## 6. 一条方法论

本次审计里最容易被漏掉的一类问题：

> **后端有、前端无**。`Client/lib/web/panel.py` 的 DISPATCH 里，
> `diagnose` / `ech` / `config_update` / `node_use` 四个动作
> **实现完整、注册完整、页面无按钮**。

如果只读文档、或只列后端函数名，会把这四项误报成"已有能力"。
反过来，只看截图也会漏掉后端已经就绪的能力。

**判断一个能力是否存在，要从用户入口倒着走一遍**：
菜单 → 页面 → 接口 → 后端。四段都通才算有。

这条和 M 项目里"配置测试通过 ≠ 能启动"是同一类教训：
**看起来有 ≠ 用户能用。**
