# 对标 SB / M 的可借鉴清单（CDN 节点 · 全协议交互 · 证书）

> 三份只读研究（SB = `/root/deepseek1/cores/sing-box-core`，M = `cores/mihomo--core`）
> 的结论汇总 + 落地顺序。**只借鉴交互与流程，不抄配置** —— SB 是 sing-box，
> M 是 mihomo，X 是 Xray，三家的传输/字段/能力边界都不一样。
>
> 用户原话：「除了协议可以是要用 X 内核特殊的东西，其他东西都可以仿着 SB 和 M。
> 唯一不同的就是协议可能支持的协议不一样、支持的选配不一样，这个是我们重点的。」

## 一、SB 怎么建一个 CDN 节点

### 交互（VLESS 为例，全部可直接回车）

```
端口       请输入监听端口 (默认: <随机>)                 ← 先问，用户可见
预置       列表 + 「不用预设, 我自己逐项配」[默认 1]
传输       1) ws 2) grpc 3) http 4) httpupgrade 5) 裸 TCP [默认 1]
证书       TLS 证书：1) 手动输入 2) 自签(pin) 3) Reality   ← 与 X 最不同的一步
接入方式   1) 直连  2) CDN 直连  3) CDN + Nginx (推荐)      ← 只在能通过时才画出来
监听       不问 —— 由接入方式决定 (cdn→0.0.0.0, cdn-nginx→127.0.0.1)
ECH        CDN 模式下才问 [默认 1 关]
收尾       自动配 nginx → [OK] 已插入 N 个站点 → 已重载 nginx
```

### 三条设计要点

**1. 「CDN 选项只在能通过时才出现」**
`sb_transport_is_http "$t" && [[ "$trusted" == "yes" ]] && can_cdn=yes`（`lib.sh:1996`）。
不能走 CDN 时，屏幕上**只有 `1) 直连`**，并附一行原因：

```
[走 CDN 需要真证书 —— Cloudflare 不接受自签证书]
[<传输> 传输不能走 CDN —— Cloudflare 只代理 ws/grpc/http/httpupgrade]
```

→ 不是"让用户选完再报错"，而是**不给不可能的选项**。

**2. 落地时再判一次（`sb_cdn_enabled`, `lib.sh:2053-2077`）**
五条全过才算 CDN：接入方式≠direct、传输 ∈ HTTP 类、证书文件在、私钥配得上、
未过期、签发者≠主体。菜单那层是"画不画选项"，这层是"真算不算 CDN"。

**3. 一个节点产出两套客户端产物**
`sb_client-<tag>.{json,yaml}`（直连版）+ `sb_client-<tag>.{json,yaml}.cdn`（CDN 版）。
「两个文件同时产出，用户按需选，互不干扰」—— CDN 挂了还能退回直连。

### nginx 侧

- 只插在**已存在的 `server_name` 块**里，找不到就拒绝（绝不猜路径）
- `BEGIN/END` 标记包裹，**替换**而非追加；插完 `nginx -t`，失败回滚
- grpc/http 与 ws 分开渲染：`grpc_pass grpcs://127.0.0.1:<port>` + `grpc_set_header Host`
- ws/httpupgrade 带 `proxy_buffering off` + 600s 超时
- 独立的 **CDN 菜单**（10 项）：插配置 / 生成整段 / 检测证书 / 列站点 /
  **列哪些节点能走 CDN（带原因）** / 生成全部 CDN 产物 / 移除 / 查残留 / 接入说明

## 二、SB / M 的全协议一键生成怎么问

### SB（头一行就把要问的一次说完）

```
════════ 全协议一键生成 ════════
交互项: 对外地址 → 证书方案 → 端口范围 → CDN → 服务器标识. 其余沿用各协议默认值.
如端口被占用或配置失败, 会自动清理; 收尾统一 check + reload.

服务端监听: :: (IPv4+IPv6 双栈, 无需选择)        ← 不问！程序能算的不问

① 客户端配置里写哪个地址 —— 别人拿到配置后连的是这个
   1) IPv4 1.2.3.4    2) IPv6 2001:...
   (选 IPv6 前请确认客户端网络真能出 IPv6 —— 写进去连不上更麻烦)

② 证书方案 —— 节点用什么证书对外服务
   1) 使用本机真实证书 (检测到 N 张 CA 可信证书)
   2) 自签证书 (伪装成随机大站域名, 客户端用 SPKI pin 锁定)
   真实证书=任何客户端都能连; 自签=仅支持 pin 的客户端能连

③ 端口范围 [回车=随机]   ④ CDN 模式 [默认开]   ⑤ 服务器标识 [旗帜+主机名]
```

**每个问题都写了「选错的后果」**，而不只是问一个值。

### M（更激进）

`1) 先预览 (dry-run, 不写入任何文件) ★推荐第一次选这个` … `2) 快速生成 端口自动分配,
不提问`。M 的 `--quick` 是真·零交互（连端口都不问），而 SB 的"快速生成"**名不副实**
（`SB_BATCH_QUICK` 没盖住端口那问和服务器标识那问，实测仍要按 2 次回车）。

**三家对比（谁更好用）**

| | SB | M | X |
|---|---|---|---|
| 交互步数 | 8–10 问 | 2–4 问 / **0 问**(--quick) | 1–2 问 |
| 首选预览 | 无 | **有 dry-run 档** | 无 |
| 重建安全 | 跳过已有 / 覆盖确认 | **失败自动还原旧节点** | **先删后建, 失败不回滚** |
| 重载后验证 | 只看 `systemctl is-active` | **真查端口绑没绑上** | 只看 `is-active` |
| 端口账本 | 每批重置 + 三重校验 | mktemp + 全量重扫 | **单调递增, 从不回收** |
| 清空时吊销分享 | 有 | 有 | **没有 revoke-all** |

## 三、SB / M 的证书管理

### SB：**只发现，不申请**

- README 原话：**「面板会列出本机检测到的真证书让你选，不会替你申请证书」**
- 全仓 grep `acme.sh --issue` / `certbot certonly` / CF API → **0 命中**
- 证书来源是外部的（KPanel 的续期脚本写 `/home/web/certs`，CF Origin 放
  `/root/catmi/cloudflare/certs`）
- 扫描目录按**优先级**排：`/home/web/certs` 排第一，理由写得很直白 ——
  「你的站点在用的那张，通常就是该用的那张」
- 去重**按域名**（不是按路径）：同一张证书常有 acme.sh 与 letsencrypt 两份，
  按路径列会让用户看到两张、编号对不上号
- 列表里标 **`← nginx 站点在用`**
- 校验只有三条：**未过期**（`-checkend 86400`）、**签发者≠主体**（判自签）、
  **私钥存在**（六种命名挨个试）。**没有**密钥/证书配对校验，**没有** CA 链校验
- 自签：EC P-256 / 200 天 / 伪装域名取自远程域名池
- **不做续期、不删证书** —— 自签证书会永久堆积

### M：比 SB 完整

- 单一真源 `src/lib/cert.sh`（658 行），全部走 `cert_ensure_safe_path`
- **真配对校验** `cert_key_match`（SPKI sha256 比对）
- **有 GC**：`cert_in_use` / `cert_gc`
- **有续期**：`mihomo-cert-sync.timer`，`OnCalendar=*-*-* 03:30:00`，
  菜单里自动装好 —— 「用户不需要知道有定时器这回事」

### 本轮 X 已经落地的（照 SB 的形状）

`证书方案` 三选一 + **每条失败路径都有下一步**：

```
证书方案 —— 这个节点用什么证书对外服务:
   1) 扫描本机已有证书 (检测到 N 张 CA 可信证书)
   2) 手动输入路径 (crt / key)
   3) 生成自签证书 (200 天; 客户端用 pin 锁定)
   真证书 = 任何客户端都能连; 自签 = 只有支持 pin 的客户端能连
```

扫不到 → 自签；路径无效 → 自签；已过期 → 自签。自签自动算 pin 进分享元数据。
CDN 档 + 自签在**生成之前**拦住（CF 不接受自签）。

### 明确**不借鉴**

| 项 | 为什么 |
|---|---|
| SB 的 8–10 问全协议模式 | 其中 7 问是协议内部选择，X 已默认得很好；X 的 1–2 问更省事 |
| SB 的"快速生成" | 名不副实（没盖住端口与标识两问）；要零交互就学 M 的 `--quick` |
| SB 的按形状清理 nginx 残留（`cdn_prune.py`） | 会误删用户自己的 `location /x { proxy_pass http://127.0.0.1:8080; }`。**X 的按标记清理更安全，不要换** |
| SB 的证书续期/GC 缺失 | X 已有 `x_cert_gc` + 引用检查；M 的 timer 可以学，SB 的"什么都不做"不要学 |
| SB 的 nginx 幂等/回滚/备份 | **X 做得更好**（`same_as_before`、备份轮转、写前 `-t`、`--require-check`）|
| SB 的端口账本 | **X 做得更好**（配置 + ss 三重收集）|
| SB 的多路复用档位 | 用户已明确否掉 X 的 mux 维度 |
| SB 的传输/字段/证书字段写法 | 不同内核，配置不可移植 |

## 五、X 真正该与 SB/M 不同的地方（用户点名的重点）

1. **协议集合**：X 只有 VLESS / VMess / Trojan / SS / Hysteria2 / SOCKS / HTTP ——
   SB 有 anytls / tuic / naive / shadowtls，X 内核不支持，不做。
2. **选配**：REALITY 传输白名单（`raw/tcp/xhttp/grpc`）、Vision 只裸 TCP、
   xhttp mode 四值、`downloadSettings` 的四条硬约束 —— 这些是 Xray 独有的，
   SB/M 没有对应物，**保持 X 自己的口径**。
3. **X 独有**：ML-KEM-768 会话加密、ML-DSA-65 握手签名、ECH、
   XHTTP 上下行分离（SB 完全没有，M 只校验不生成）。
4. **mihomo YAML 产物**：X 现在建节点即产出（含 `download-settings`），
   SB 有等价物（`to_mihomo.py`），M 没有独立转换器。
