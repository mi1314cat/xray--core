## 一、对外地址探测（X 最大的基建缺口）

### X 的现状：6 处各写各的

```
conf/outbound.sh:1176      读网口 + 私网过滤（像 SB）
conf/hysteria2.sh:638      curl ip.sb
conf/Shadowsocks.sh:364    hostname -I
conf/http.sh:104           只判断"有没有 v4"
conf/fd/legacy/…            api.ipify.org
conf/outbound.sh:2047      依次试 api.ipify.org / ifconfig.me / ipinfo.io
```

同一个坑要修 6 遍，而且总有一两处漏掉。**实测漏掉的那次**：分享链接里下发的是
WARP 出口地址 `104.28.201.80`，而服务器入站是 `107.173.154.178` —— 客户端照着连
必然不通，而链接看起来完全正常。

### SB 的做法

```bash
default_server_ip() {   # src/conf/lib.sh:472
    # 1. 读网口, 排除私网
    ip -4 -o addr show scope global | awk '{print $4}' | cut -d/ -f1 |
        grep -vE '^(127\.|10\.|172\.(1[6-9]|…)|192\.168\.)' | head -1
    # 2. 外部服务兜底
    curl -4 -s --max-time 8 ip.sb
    # 3. 真实 IPv6（排除隧道）
    sb_real_ipv6
}
```

### M 的做法（最完整，建议以它为准）

`src/lib/env.sh` 有一整套：

| 函数 | 作用 |
|---|---|
| `m_addr_is_local` | **地址在不在本机接口上** —— 把外部答案变成可信的关键一步 |
| `m_iface_public_addr` | 读网口，排除隧道/虚拟网卡与私网 |
| `m_addr6_real` | 真实 IPv6（排除隧道接口） |
| `m_warp_active` | 本机是否在走 WARP/隧道 |
| `m_is_private_addr` | 不可路由/保留段判定 |
| `M_TUNNEL_IFACE_RE` | 隧道接口名正则 |

**顺序**：传参 → 已保存的（**过自检**）→ 本机接口（排除隧道与私网）→ 外部探测+自检 → 含私网的接口。

### 从 M 的注释里学到的四条实战教训

1. **反向写法（先问外部再自检）是错的**：套了 WARP 时那条查询本身走隧道，拿回来
   必然是 WARP 地址，然后自检丢掉 —— 每次白跑一趟网络还刷一堆警告。实测那一次
   输出 **10 行 [Warn]**，而结论其实完全正确。**逻辑对、呈现糟**。
2. **已保存的地址必须过自检**：不加这一关，修复前存进去的 WARP 地址会被一直沿用，
   自检形同虚设（实测写进配置 13/13 全连不上）。
3. **`he-ipv6` 与 `he-ipv6-tun` 要分清**：前者是 HE 隧道服务商给的**公网可路由**
   地址，必须保留；后者是隧道内层口。正则写成 `he-ipv6.*` 会把真实地址一起排掉
   —— 明明有 IPv6 却判成"无"。
4. **198.18.0.0/15 必须排除**：那是 mihomo/Clash 默认的 fake-ip 段，机器上跑着 TUN
   时网口扫描会挑中 `198.18.0.1`，客户端拿去连必然失败。

### X 的动作

## 二、取文件：镜像链（X 完全没有）

M 的 `install.sh` 有 `REPO_MIRRORS` 链 + `_pick_source` + `fetch` / `fetch_repo`：

```bash
REPO_MIRRORS=(
    "https://ghproxy.net/https://raw.githubusercontent.com/…"
    "https://gh-proxy.com/https://raw.githubusercontent.com/…"
    "${REPO_PROXY:-https://cfgithub.gw2333.workers.dev/…}"
    "https://cdn.jsdelivr.net/gh/mi1314cat/mihomo--core@main"
    "https://fastly.jsdelivr.net/gh/mi1314cat/mihomo--core@main"
)
```

**顺序的讲究（注释原文）**：

- ghproxy / gh-proxy 是**实时回源**的，能立刻拿到刚推上去的版本
- **jsdelivr 是 CDN 带缓存的** —— 实测推完 commit 后它仍返回旧文件，加时间戳也
  绕不过去。所以只能放最后兜底
- cfgithub 在部分机器上直接超时，排中间

**探测参数也是踩出来的**：每个源探测 **25 秒且试两次**。原注释：

> 实测：github.com 在那台机器上是连接超时而非拒绝，12 秒的探测窗口会把本来能用
> 的镜像也判成"不通"，结果整条链全废、安装直接卡死。

**第二轮**：按可靠性找本机代理，带着它把整条链再走一遍。

### X 的现状与动作

X 面板 19/20 项直接 `bash <(curl -Ls github.com/…/raw/refs/heads/main/…)`，
**没有任何镜像与重试**。本次实测还踩到：push 后约 5 分钟内 raw 仍返回旧内容
（GitHub CDN 缓存）—— 与 M 注释里记的 jsdelivr 缓存是同一类问题的两层。

**待办**：抽出 `conf/lib/fetch.sh`（镜像链 + 探测 + 代理回退），各脚本改用它。

## 三、入口脚本：客户端 / 服务端区分

| | 入口 | 区分方式 |
|---|---|---|
| M | `install.sh` | `install.sh` / `install.sh server` / `install.sh client`，装到不同目录，systemd 服务名不同 |

M 的形态最好：一个引导脚本，无参进选择菜单，带参直接装对应角色。

**待办**：X 加统一的 `install.sh`（或 `xray.sh`）引导，`server|client` 两个角色。

## 五、节点命名

SB 的 tag 形如 `vmess01-TLS-CDN`、`anytls02-REALITY` —— **协议+两位编号+传输+安全**
的组合，一眼能看出节点是什么。M 类似。

—— 大小写与分隔符**不统一**（`_` 与 `-` 混用，大小写混用）。

**待办**：统一命名约定，并让默认值带上 `X`（便于跨内核辨认是谁建的节点）。

## 六、CDN → Nginx

SB 有专门的 `src/conf/cdn.sh` + `cdn_menu.sh` + `cdn_nginx.sh` + `cdn_apply.py`：

```
cdn_transport_supported   哪种传输能走 CDN
cdn_config_supported      哪种配置能走 CDN
```

**待办**：抽 `conf/cdn.sh`（含 `cdn_cleanup_stale` 这个必须的清理）。
